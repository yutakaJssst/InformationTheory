## 最初は避けるもの、発展では使えるもの

第11回の最小構成は止まりにくい形にする。第12回以降の発展機能では、必要に応じて挑戦してよい。

| 第11回では避ける | 第12回以降の発展なら可 |
|---|---|
| ログイン必須の本格サービス | ログインなしで使える範囲に限定 |
| 外部APIだけに依存する構成 | APIキー管理、料金、代替手段を説明できる場合 |
| スマホアプリのストア公開 | ブラウザで動くプロトタイプ |
| 複雑なデータベース設計 | CSV、JSON、localStorageから始める |
| 個人情報・未公開研究データ | ダミーデータ、公開データ、匿名化データを使う |

### 推奨

- HTML/CSS/JavaScriptだけで動くWebアプリ
- Python + Streamlitなどの小さなWebアプリ
- CSVやJSONを使う簡単なデータ管理アプリ
- Excel、API、AIモデル連携は、最小限動く版ができた後の発展候補にする

# テーマを決める
自分の小さな不便をアプリに変える

---

## テーマ選びの条件

次の5つを満たすテーマにする。

| 条件 | 確認すること |
|---|---|
| 自分ごと | 自分、研究室、周囲の人が実際に使いそうか |
| 小さい | 最初の機能を1つに絞れるか |
| 入力がある | ユーザーが何かを登録・選択・入力するか |
| 出力がある | 一覧、結果、チェック、可視化が出るか |
| 検証できる | 操作して「動いた/動かない」を判断できるか |

<span class="teal">よいテーマは「大きな社会課題」より「小さく確かめられる困りごと」から始まる。</span>

---

## テーマ候補の例

| テーマ | 最初に作る機能 |
|---|---|
| 論文メモ管理 | 論文タイトル、URL、メモを登録し一覧表示 |
| 実験ログ整理 | 日付、条件、結果メモを登録しCSV保存 |
| 発表練習タイマー | 発表時間を設定し、残り時間を表示 |
| 研究進捗ToDo | タスク、期限、状態を登録し一覧表示 |
| プロンプト記録 | プロンプト、結果、修正点を保存 |
| 支出メモ | 品目、金額、日付を登録し合計表示 |
| 忘れ物チェック | 持ち物リストを作り、チェック状態を保存 |

<div class="callout">
まずは「登録する」「一覧する」「状態を変える」のどれかを動かす。そこから発展させる。
</div>

最小構成が動いたら、第12回で「使えるアプリ」に近づける。

| テーマ | 最小構成 | 発展機能・検証の例 |
|---|---|---|
| 実験ログ整理 | 条件と結果を保存 | CSV読込、グラフ化、手作業との時間比較 |
| 英語学習支援 | 問題を出す | 間違い傾向の分析、弱点問題の生成 |
| Excelグラフ支援 | 表からグラフ作成 | 軸設定、対数表示、手作業グラフとの比較 |
| 論文メモ管理 | メモ一覧 | タグ検索、要約、後で探せたかの確認 |
| 音声・画像処理 | ファイルを読み込む | 分離、変換、処理前後の比較 |

<span class="orange">発展機能は「便利そう」ではなく、デモと検証で見せられるものを選ぶ。</span>

## テーマ候補を3つ出す

### 手順

1. 自分が最近少し困ったことを3つ書く
2. それぞれをアプリにすると何を入力・出力するか考える
3. Miroに候補を貼り、実現しやすさを比べる

### Miroに書くこと

| 項目 | 内容 |
|---|---|
| 困りごと | 何が面倒か、どこで時間がかかるか |
| 利用者 | 誰が使うか |
| 入力 | ユーザーが入力するもの |
| 出力 | 画面に表示するもの |
| 検証 | 何ができれば役に立ったと言えるか |

# 要件を決める
作るものと作らないものを分ける

---

## 要件定義は難しい言葉ではない

ここでは、次の3点をはっきりさせる作業と考える。

1. 誰のためのアプリか
2. 何ができれば役に立つか
3. 今回は何を作らないか

<div class="flow">
課題 → 利用者 → 必要な機能 → 最小構成 → 実装 → 動作確認
</div>

<div class="callout">
AIに実装を依頼する前に、要件が曖昧だと、AIは勝手に仕様を補ってしまう。
</div>

---

## 機能要求と非機能要求

| 種類 | 意味 | 例 |
|---|---|---|
| 機能要求 | アプリが何をするか | メモを登録する、一覧表示する |
| 非機能要求 | どう動いてほしいか | 直感的に使える、データを保存できる |

### 今回の目安

- 機能要求: 5個程度
- 非機能要求: 3個程度
- 最初に作る機能: そのうち1〜2個だけ

<span class="orange">最初から機能を増やさない。増やすのは、最初の機能が動いてから。</span>

---

## 要件の書き方

### ユーザーストーリー

> [利用者]として、[目的]のために、[機能]を使いたい。

### 例

| 利用者 | 目的 | 機能 |
|---|---|---|
| 大学院生として | 読んだ論文を後から探すために | 論文タイトルとメモを登録したい |
| 発表練習者として | 時間配分を守るために | 残り時間を表示したい |
| 実験者として | 条件と結果を忘れないために | 実験ログを日付つきで保存したい |

---

## Miroで要件を整理する

Miroに次の列を作り、付箋で埋める。

| 列 | 書くこと |
|---|---|
| 利用者 | 誰が使うか |
| 困りごと | 何が面倒・不便なのか |
| 入力 | ユーザーが登録・選択・アップロードするもの |
| 出力 | 画面に表示する結果、一覧、グラフ、判定 |
| 機能 | できるとよいことを5個程度 |
| 作らない機能 | 今回は入れないもの |

<div class="callout">
要件定義は、正しい文章を書く作業ではなく、作るものと作らないものを見えるようにする作業。
</div>

---

## Miroで決めること

最後に、Miro上で次の4つをはっきりさせる。

| 項目 | 内容 |
|---|---|
| 今日作る最小構成 | 最初に動かす1〜2機能 |
| 第12回の発展候補 | 追加したい機能を1〜2個 |
| 第13回のデモ | 何を入力し、何を見せるか |
| 検証方法 | 時間短縮、比較、正しさ、使いやすさ、限界 |

<span class="teal">このMiroの内容を、そのまま実装依頼プロンプトやREADMEの材料にする。</span>

---

## 最小構成のアプリを決める

この授業では、最小構成のアプリを「最小限でも、実際に使える形になっているもの」と考える。

<div class="callout">
第11回で作るものは完成形ではない。第12回で発展させるための、壊れにくい土台にする。
</div>

### よくない最小構成

- ログイン、グラフ、共有、通知、AI要約まで全部入れる
- 画面だけ作って、保存や出力が確認できない
- コードはあるが、使い方が説明できない

### よい最小構成

- 入力 → 保存 → 表示 の流れが1本通る
- 使い方を3ステップで説明できる
- 動いたかどうかを自分で確認できる

---

## 今日の実装対象を1つに絞る

| アプリ例 | 今日作る機能 | 次回の発展候補 |
|---|---|---|
| 論文メモ帳 | 論文メモを登録し一覧表示 | 検索、タグ、要約 |
| 支出メモ | 支出を登録し合計表示 | グラフ、月別集計 |
| 発表タイマー | 時間を入力しカウントダウン | 履歴保存、警告表示 |
| 実験ログ | 条件と結果メモを保存 | CSV読込、グラフ化 |

# AIに実装を依頼する
文脈、範囲、完了条件を渡す

---

## AIを使った開発の基本サイクル

```text
1. 要件を渡す
   利用者、課題、最初に作る機能、作らない機能

2. 小さく実装してもらう
   1つの画面、1つの機能に絞る

3. 実行して確認する
   表示、入力、保存、エラーを確認

4. 結果をもとに直す
   期待した動作と実際の動作を伝える

5. 記録する
   README、プロンプト、修正点を残す
```

---

## 実装依頼プロンプトの型

<div class="prompt-box">
あなたは大学院生のPBLを支援するソフトウェア開発者です。<br>
次の条件で、最小構成のアプリのコード案を作成してください。<br><br>
【アプリ名】[アプリ名]<br>
【利用者】[誰が使うか]<br>
【解決したい課題】[何を楽にしたいか]<br>
【技術】[HTML/CSS/JavaScript または Python + Streamlit]<br>
【今日作る機能】[1つの機能]<br>
【入力】[ユーザーが入力する値]<br>
【出力】[画面に表示する結果]<br>
【保存】[localStorage / CSV / JSON / 保存なし]<br>
【第12回の発展候補】[追加したい機能を1〜2つ]<br>
【検証方法】[何を試せば役に立つと判断できるか]<br>
【今回は作らない機能】[3つ程度]<br>
【完了条件】[何ができれば成功か]<br><br>
必要なファイル構成、コード、実行方法、動作確認手順を示してください。
</div>

## 技術選択の目安

| 選択肢 | 向いている場合 | 注意点 |
|---|---|---|
| HTML/CSS/JavaScript | ブラウザだけで動かしたい | 保存はまず `localStorage` が簡単 |
| Python + Streamlit | データ処理や可視化をしたい | 実行環境の準備が必要 |
| Python CLI | 画面より処理を重視したい | 第13回でデモしやすい形にする |
| API・AIモデル連携 | 発展機能として外部情報やAI処理を使いたい | APIキー、料金、代替手段を確認 |
| Excel・CSV処理 | 実験・研究データを扱いたい | 公開データやダミーデータで確認 |

### 今日のおすすめ

迷ったら、HTML/CSS/JavaScriptの1画面アプリから始める。  
ファイルを開くだけで動作確認でき、発表で見せやすい。

<span class="orange">AIが本格的な構成を勧めてきたら、なぜ必要かを確認する。説明できなければ、今回は選ばない。</span>

## 技術選択もAIに相談する

言語やフレームワークを知っている前提にはしない。  
AIには「候補を比較」させ、理由を見て自分で選ぶ。

<div class="prompt-box">
私は情報論のPBLで小さなアプリを作ります。<br>
プログラミング経験は [ほとんどない / Pythonを少し / HTMLを少し] です。<br><br>
【作りたいアプリ】[例: 論文メモを登録して一覧表示するアプリ]<br>
【必要な機能】[入力、保存、一覧表示など]<br>
【発表まで】2週間<br>
【条件】環境構築で詰まりにくい / 第13回でデモしやすい / 無料で使える<br><br>
HTML/CSS/JavaScript、Python + Streamlit、Python CLIなどを比較し、今回どれがよいか理由つきで提案してください。難しすぎる構成は避けてください。
</div>

<span class="teal">React、Next.js、Django、Docker、スマホアプリは、必要性を説明できる場合だけ使う。</span>

## データとAPIキーの注意

研究や実験に関係するアプリほど、扱うデータに注意する。

| 対象 | 授業での扱い |
|---|---|
| 個人情報 | 使わない |
| 未公開の研究データ | そのままAIに入れない |
| 研究室の内部資料 | ダミー化、匿名化、要約して使う |
| APIキー | コードに直接書かない。公開リポジトリに置かない |
| 公開データ | 出典をREADMEに書く |

<div class="callout warning">
AIに入力してよい情報か迷ったら、ダミーデータで開発する。
</div>

## AI出力を受け取ったら確認すること

| 観点 | 確認内容 |
|---|---|
| 実行 | 指示通りに起動できるか |
| 表示 | 画面が崩れていないか |
| 入力 | 空欄や変な値で壊れないか |
| 保存 | 更新後もデータが残るか |
| 範囲 | 今回作らない機能を勝手に作っていないか |
| 説明 | 自分がコードの役割を説明できるか |

<div class="callout">

</div>

## 第13回で示す検証

アプリの種類に合わせて、1つ以上示す。

| 検証の種類 | 例 |
|---|---|
| 時間短縮 | 手作業3分が、アプリで30秒になった |
| 正しさ | 理論値、既存ツール、手計算の結果と比べる |
| 使いやすさ | 自分または友人が、説明なしで操作できたか |
| 改善 | 初期版の失敗を直し、どこが良くなったか |
| 限界 | まだできないこと、間違いやすい条件を説明する |

<span class="teal">検証は大げさでなくてよい。自分で確かめた事実を示す。</span>

## 最小構成のアプリを作る

### 手順

1. Miroで整理した要件を見ながら、実装依頼プロンプトを埋める
2. AIにコード案を出してもらう
3. ローカルで実行する
4. 1つ以上の入力例で動作確認する
5. うまく動かなければ、エラー時プロンプトで修正する

### ここで残す記録

- 最初に送ったプロンプト
- AIの出力をそのまま使えなかった箇所

- 第13回で検証したいこと
